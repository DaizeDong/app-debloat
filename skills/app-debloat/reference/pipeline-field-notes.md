# Pipeline: Field Notes for P5 to P7

Lessons from the first live apply, verify and install runs, organized by stage. They extend `pipeline-apply.md` (the stage steps and exit criteria) and do not replace it. Examples are synthetic (`ExampleApp` by `AcmeCorp`).

## P5 Build: Known Failures

A failure that is understood and accepted is recorded, never ignored. Typical cases: a security suite vetoes one service change (`safety.md`, Antivirus), or a service is driver-protected.

- Give the manifest action a `knownFailure {reason, ref}` field. `reason` is one sentence a reader of `auto.log` understands; `ref` is the ledger ID that holds the evidence (the error text, the service's permission list and protection level, loaded minifilters, installed AV).
- Each run then logs that item as WARN with the reason instead of counting it as a failure, so a new failure still shows as one and the run history can be clean.
- Close the path with another lever and list both in `plan.md` (for example `A-07` service disable with `knownFailure`, then `A-08` task disable and `A-09` firewall rule for the same updater).
- Never set `knownFailure` to silence a failure nobody has explained. Without a ledger entry it is not known.
- Look for System event 7006 within a few seconds of the failure: `Get-WinEvent -FilterHashtable @{ LogName = 'System'; Id = 7006; StartTime = <failure time minus 10 s> }`. A line such as "The ScRegSetValueExW call failed for Start with the following error: Access is denied." shows the denial was on the service's `Start` registry value, a registry-level veto (typically a security suite's registry filter), not the service's permissions. The event names no service, so match it to the failed `sc.exe config` by timestamp, one event per denied change. Add it as an anchor (`log` type, `source` System 7006, `time`, `line`) on the knownFailure's ledger entry, with a dated note saying what it shows (`ledger.md`, File and Format).

```json
{ "id": "A-07", "type": "service-disable", "target": ["AcmeUpdateSvc"],
  "knownFailure": { "reason": "security suite denies service config changes for this service", "ref": "L-RI-012" } }
```

**Processes the Loaded-Module Check Cannot Inspect.** Before a placeholder on a DLL, the engine checks that no process has it loaded. Some processes cannot load app code and cannot be opened either: VBS trustlets such as `LsaIso.exe` and `NgcIso.exe` (OpenProcess error 998) and VM memory processes such as `vmmem*` (error 5). If they defer an action every time, name them with the manifest field `checkLoadedExempt` or the engine switch `-IgnoreUninspectable <process names>`. The run prints the skipped processes and journals the choice. Record each name with its error code in the ledger. Never exempt a process that could host the app's code (Explorer, a browser, any process whose image is under a resolved root, any process that failed for a reason other than isolation).

## P6 Verify

**Connection Burst or Retry Loop.** One socket count right after start cannot tell them apart; a client may open about 50 sockets in its first half minute and settle. Take 3 or more counts over at least 2 minutes and compare each with the before snapshot taken at the same time after start. A burst decays; a retry loop stays flat or grows, and repeats the same remote at a fixed interval. Count like for like: the same tool and the same filter for both sides (for example `Get-NetTCPConnection -OwningProcess <pid>`, established only). Different tools count differently, so never compare an inventory figure with a live filtered count. `launch_monitor.ps1` takes these counts itself: a `conn_count` line every `-ConnCountEverySeconds` (default 60) with the established TCP connections per tracked process and in total. A 20-minute capture before and after apply gives 20 counts on each side at the same times after start; compare those, not counts taken by hand.

**Generic Process Names Are Not the App.** A name match from `launch_monitor.ps1 -WatchNames` (or any name poller) on a generic name such as `updater.exe` or `setup.exe` counts as the app's process only through its image path under a root, its service binary (the line's `service_image`, `under_root: true`), a tracked app process as its parent (`reason` `child`), or a line in the vendor's own log at the same time. A parent of `services.exe` says only that a service started it; other vendors' updaters run the same way. Example: `updater.exe` under `services.exe` with `service_image` `%ProgramFiles%\OtherVendor\Update\updater.exe` and `under_root: false` is another vendor's updater, even when it appears right after `ExampleApp.exe` starts; the same name with `service_image` `%ProgramFiles%\AcmeCorp\Update\updater.exe` under the app's root is the app's. Without one of these ties it stays a `hypothesis`.

**Restore-Pages Bubble.** After `stop_app.ps1` forced a Chromium-based app closed, its next start may show a small "restore pages?" bubble, likely a side effect of the forced close. `shot_windows.ps1` tags a small window whose title matches it (English and Chinese) as `restore_pages_bubble` with `bubble_match: title`. Forks localize it or leave its title empty, so for the first capture after a forced stop pass `-AfterForcedStop`: a small untitled `Chrome_WidgetWin_*` window (at most 600x400 at 96 DPI) beside a main window of the same process then gets `bubble_match: shape` and is counted under `possible_restore_bubbles`. Electron and CEF apps use the same window class and a small untitled popup has the same shape, so look at the capture before ruling a shape match out. Note it in `verification.md` next to the screenshot, and judge popups from a start that followed a normal close.

**32-Bit Modules.** `Get-Process` from 64-bit PowerShell lists only the exe for a WOW64 process. Use `scripts/list_modules.ps1 -Pid <pid>` or `-ImagePathRegex <regex>`: it walks Toolhelp32 including 32-bit modules and changes nothing. Use it to prove a blocked DLL is no longer loaded and a kept one still is.

**Planned Removals Are Not Drift.** Run `snapshot_diff.py <before> <after> --journal <journal.jsonl>` (or `--expect-removed <file>` with one planned path per line) so files the apply removed or replaced on purpose are marked expected. Only unexplained changes keep the "binary fingerprint changed" warning, and those still mean P1 to P3 must be re-run. Two other kinds of noise: a path that differs only in letter case is the same Windows path, and the agent's own shells can show up because their command lines contain the app name; tag those as self, not as app processes.

**The App's Own Log.** Many clients keep a diagnostic log (for example JSON lines with a `level` field). Compare its error and warning lines in the same window after start, before and after apply. It is often the best evidence that the blocked parts cause no errors in the core workflow. Summarize the relevant lines in `verification.md`; do not copy the log into DATA. Two traps:
- Event counts in the app's own log (clicks, views, impressions) are not evidence of user activity. Apps log synthetic events: a session with no input at all can show `"event":"click"` twelve times. Judge activity by the no-input rule you followed, not by the log.
- Log timestamps may be UTC, marked with a `Z` (`2030-01-01T14:05:09Z`) or with no offset at all. Convert them to local time before matching them with `history.log` or screenshot times: `[datetime]::Parse('2030-01-01T14:05:09Z').ToLocalTime()`. When a log gives no offset, place one event you know (the app's own start) to learn which clock it uses before trusting the rest. `launch_monitor.ps1` writes `ts` and `created` in UTC, so compare those with the log's UTC times directly.

**Core Functions That Need Input.** Under a no-input rule a lookup, OCR, document translation or an upload cannot be exercised. Do not mark them passed. Move them to the owner's after-reboot list in `verification.md` with exact steps and the pass condition. Typing is allowed only into a window the agent itself opened (`safety.md`, Keystrokes).

**Scratch.** Transcripts and small captures go to the run's scratch folder in the private companion. Delete scratch files over 50 MB once their findings are in the ledger (`safety.md`, Public Versus Private Data).

## P7 Keep Applied

- Run `-Install` only after a clean `-Apply`: P6 passed, and a second `-Apply` reports only SKIP plus WARN lines from `knownFailure` items. An apply that exits non-zero for any other reason must be fixed first.
- Check the exit code of `-Install` itself. If its apply step failed, the watch task is not registered (the output says so); a task from an earlier `-Install` stays until `-Uninstall`. Fix the failure and run `-Install` again.
- Start the first watched run by hand rather than waiting for logon: `Start-ScheduledTask -TaskName <Prefix>Debloat-Watch`. A non-elevated shell can start the owner's own watch task (registered for the owner at the Highest run level), so no UAC prompt is needed. Then poll until the run is over: `(Get-ScheduledTask -TaskName <Prefix>Debloat-Watch).State` is `Ready` again and `(Get-ScheduledTaskInfo -TaskName <Prefix>Debloat-Watch).LastTaskResult` is no longer 267009 (0x41301, "task is currently running"), which it reads right after the start. Judge the run by the new line in `history.log` in the state dir, `0 failure(s)` plus its WARN and FAIL text, not by `LastTaskResult`: the task's action runs the script through `conhost.exe --headless`, which does not pass the script's exit code on, so a run whose line shows 1 failure can still report `LastTaskResult` 0.
- Owner choices that were tried as options become defaults only after the owner ran the core test (for a drive: a real upload and download) and one reboot (`plan-template.md`, Rules That Apply to Every Section).
