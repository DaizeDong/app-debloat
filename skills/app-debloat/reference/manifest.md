# Manifest and Engine Reference

A per-app script is built from three parts: `templates/app-debloat.template.ps1`, a JSON manifest, and optional
hook scriptblocks. `scripts/DebloatEngine.ps1` is inlined at build time, so the user downloads one file.

```powershell
. .\scripts\DebloatEngine.ps1
New-AppScript -ManifestPath manifest.json -HooksPath hooks.ps1 -OutFile <Prefix>Debloat.ps1
```

`New-AppScript` validates the manifest, turns every `options[]` entry into a `[switch]` parameter, writes UTF-8
with BOM and CRLF, and refuses output that does not parse. It prints `[WARN] option -X gates no action` for an
option that no action names in `when` or `unless` (typically left behind when its actions were removed); the
built script lists such options under `Unused Options` instead of `Options Not Selected`. Worked examples (synthetic): `examples/contoso-pinyin`
(IME, with a hook) and `examples/fabrikam-drive` (Electron netdisk), both generated by `tools/make_fixtures.py`.

## Top-Level Fields

| Field | Meaning |
|---|---|
| `schema` | `2` (required: evidence per action, `version.supported.versions`, `installRoot.identity`) |
| `id` | lowercase id; state lives in `%ProgramData%\AppDebloat\<id>` |
| `name` | display name |
| `taskPrefix` | alphanumeric; tasks are `<Prefix>Debloat-Watch`, `-Preboot-<action>`, `-Restore-<action>` |
| `profile` | free text, the reference profile used (ime, electron-netdisk, ...) |
| `riskTier` | `normal` or `out-of-process-only` (refuses every file change inside the install root) |
| `installRoot` | how to find the install, see below |
| `versionDir` | optional: per-version subfolder, exposed as `{ver}` (else `{ver}` = `{root}`) |
| `pathVars` | optional named folders outside the root: `{"userData": {"envVar": "X", "default": "%USERPROFILE%\\..."}}` |
| `allowedRoots` | extra folders the engine may change (tokens allowed); each is refused if it is, or contains, a system location |
| `version` | fingerprint sources and the list of supported (inspected) versions |
| `core` | the core-function contract |
| `options` | `[{name, default, help}]`, become switches; actions opt in with `when` / `unless`. An option that enables an `inferred` or `hypothesis` action must default to false; its `help` names the probe that would promote the action |
| `checkLoadedExempt` | optional process names (wildcards allowed, `.exe` optional, not only wildcards) that the loaded-module check skips when they cannot be inspected; same meaning as `-IgnoreUninspectable`, and the one the watch task uses (see Loaded-Module Check) |
| `actions` | ordered list; executed in this order |

**installRoot** (first hit wins): the `-InstallRoot` parameter, then `envVar`, then the Uninstall entry matched by
`uninstall.displayName` / `uninstall.publisher` regexes (HKLM 64, HKLM 32, HKCU; uses `InstallLocation`, then the
folder of `DisplayIcon`, then of `UninstallString`), then `service.name` ImagePath folder (`levelsUp` parents up),
then `candidates[]`. A candidate counts only if every `mustContain` entry exists in it and it passes `identity`.
Never hard-code a drive.

Every Uninstall entry that matches is collected, not only the first. When the matches carry different
`InstallLocation` values (one vendor shipping a browser and a netdisk under similar names, for example), the
engine prints a WARN that lists each entry (DisplayName, version, location, registry key and view) and tries
them in lookup order; `mustContain` and `identity` decide. Narrow `displayName` or add `publisher` when the WARN
appears. The `uninstall` version source reads the entry that the chosen root came from; when the root came from
another source it reads the entry whose `InstallLocation` is that root, or the single match, else nothing.

Every plan starts with a header that says how the root was found and which identity check passed:

```
Install root  : C:\Program Files (x86)\ExampleApp
Found by      : Uninstall InstallLocation of 'ExampleApp' (HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\ExampleApp (32-bit view))
Identity      : passed (signer 'CN=AcmeCorp, O=AcmeCorp' on ExampleApp.exe; text check resources\build-info.json matches /.../)
```

`Found by` is one of `-InstallRoot override`, `environment variable <name>`, `Uninstall InstallLocation|DisplayIcon|
UninstallString of '<DisplayName>' (<key> (<view>))`, `service <name> ImagePath` or `candidate <pattern>`.

**installRoot.identity** (required): vendor checks that a look-alike folder cannot pass by file names alone. They
apply to every candidate, the `-InstallRoot` parameter and the environment variable included. An explicit
override (parameter or env var) that fails `mustContain` or `identity` is refused (exit 2); it never falls through
to another candidate. Discovered candidates that fail are skipped with a WARN.

| Key | Check |
|---|---|
| `signer` | `{files: [relative paths], subject: regex}`: each file has a `Valid` Authenticode signature whose signer subject matches. Use it whenever the vendor signs its binaries |
| `text` | `[{file, regex}]`: a vendor file (product manifest, `build-info.json`, an INI) exists and its text matches |
| `files` | `[relative paths]`: extra files that must exist (weak alone; at least one of `signer` or `text` is required) |

```json
"identity": { "signer": { "files": ["ExampleApp.exe"], "subject": "CN=AcmeCorp" },
              "text": [ { "file": "resources\\build-info.json", "regex": "\"name\"\\s*:\\s*\"example-app\"" } ] }
```

After the root is chosen the engine resolves its real path (`GetFinalPathNameByHandle`: junctions, symlinks and
`subst` drives followed, including every ancestor above the root) and applies the system-location refusals to both
the written and the real path. The same is done for every `allowedRoots` entry, and for every target before it is
changed (see Safety rules).

**versionDir**: `registry {path, name}` names the active version when it exists with `mustContain`; otherwise the
highest folder matching `pattern` that contains `mustContain`.

**version.sources** (first non-empty wins): `registry {path, name, view}`, `uninstall` (DisplayVersion of the
matched entry), `file {path}` (FileVersion), `dirname` (name of `{ver}`), `text {path, regex}` (capture group 1).
Each entry is flat and names its kind in `source`, for example
`{"source": "file", "path": "{root}\\App.exe"}`. A nested shape such as `{"file": {"path": ...}}` is rejected
when the script is built, because it would resolve no version and make every `-Apply` refuse. The dry run warns
when no source returns a version.
`supported` lists the versions the inventory actually inspected:

```json
"supported": { "versions": ["12.4.0.1234", "12.3.9.1000"] }
```

A version matches when it equals a listed string (or the same dotted number). A range is accepted only when the
manifest opts in explicitly with `"allowRange": true, "min": "...", "max": "..."`; leave it out unless every
version in the range was inspected. A version that is not supported, or that could not be read at all, is refused
by `-Apply`, `-Install` and `-Auto` (exit 2, nothing changed) unless `-Force` is passed. `-Auto` additionally writes
a `REFUSED ... WARN:` line to `history.log`; since the watch task never passes `-Force`, an update to an unlisted
version stops re-application until the manifest is rebuilt. The dry run prints a WARN and still shows the plan.
The fingerprint is `version|versionDirName`; `-Auto` writes a WARN to history.log when it changes.

**core**: `files` (paths or globs, may not be changed in any way, nor any folder that contains them),
`preserve` (paths or globs of settings files that must survive but whose content may be edited: see below),
`processes` (never stopped, never IFEO-blocked), `restartable` (core processes the app relaunches by itself: may
be stopped to unload a DLL, never blocked), `services` (never disabled), `probe` (prose: how P6 proves core
function works).

**core.preserve versus core.files.** A file in `core.files` is untouchable: no action, hook or edit may change it.
A file in `core.preserve` may not be replaced, deleted, locked or put behind a placeholder, and neither may a folder
that contains it, but its content may be edited in place by `ini-set`, `json-set`, `preboot-file-edit` and by a
hook that calls `Assert-AdPathSafe <path> -EditInPlace`. Use it for the config file the app needs at start and
that also holds the ad or AI switch (`{userData}\config.ini`, a Chromium `Preferences` file):

```json
"core": { "files": ["{root}\\ExampleApp.exe"], "preserve": ["{userData}\\config.ini"] }
```

Path tokens everywhere: `{root}`, `{ver}`, `{<pathVar>}`, `%ENV%`. The install root token is `{root}`; there is no
`%ROOT%`. `*` and `?` expand against existing items.

## Actions

Common fields: `id`, `type`, `category` (`ad`, `ai`, `telemetry`, `updater`, `repair`, `promo`), `rationale`
(ledger item ids, required), `evidence` (required, see below), `evidenceNote` (what is unproven), `reversible`
(default true; false items are left alone by `-Uninstall`), `reapply` (true only for blocking actions: the watch
task re-confirms them), `effect` (`block` default, or `reset`; `reset` with `reapply: true` is rejected), `when` /
`unless` (option name), `backup` (placeholder types only, default true; see the table), `knownFailure`
(`{reason, ref}` for the whole action, or `{reason, ref, targets}` for some of its items, see Known Failures).

**evidence** is the weakest ledger status among the action's `rationale` entries, copied verbatim
(`reference/ledger.md`): `observed`, `anchored`, `inferred` or `hypothesis`.

- `observed` and `anchored` actions are active by default.
- `inferred` and `hypothesis` actions are INACTIVE by default. They must name their enabling option in `when`
  (that option must default to false, and `unless` is not allowed on them). They run only when the user passes that
  switch; `-Install` saves it, so `-Auto` keeps re-applying an action the user enabled.
- Every plan (dry run, `-Apply`, `-Install`, `-Auto`) prints the inactive actions after the numbered changes:

```
[INACTIVE] [updater-exe] file-placeholder-dir, updater: evidence is hypothesis (client tolerance of a missing updater is untested). Enable with -RemoveUpdaterExe
```

  and each planned item shows its status (`file-placeholder-dir, updater, evidence observed, reapply`).
- Every plan except `-Auto` then prints an `Options Not Selected` section (options that gate no action are listed
  apart, under `Unused Options`, as `unused option -X`): each option that was not passed, the
  action ids it would enable (`when`) or skip (`unless`), their evidence (with `evidenceNote` for inferred and
  hypothesis), and the option's help. An option-gated action is therefore visible even when its evidence is
  observed:

```
Options Not Selected: 2 (pass the switch to select it)
  -BlockNet: enables net (observed)
      Also firewall ContosoTool.exe (it fetches skins and cell dictionaries too).
  -KeepAi: skips ai-plugin (observed), ai-entry (observed)
      Keep the AI assistant plugin.
```

- `New-AppScript` appends the same list to the option's help text (`Enables: id (evidence), ...`, `Skips: ...`),
  so `Get-Help .\<Prefix>Debloat.ps1 -Parameter <Option>` shows it.

Every undo first compares the current state with the state the tool wrote (the journal's `after`). It restores the
original only when they are equal, reports SKIP when the original is already back, GONE when the object no longer
exists, and CONFLICT (left untouched) for anything else.

| type | fields | does | undo (only from the state the tool wrote) |
|---|---|---|---|
| `service-disable` | `target[]` names, `stop` | `sc config start= disabled`, stops it if running | if still Disabled, restores Auto (delayed-auto kept) or Manual |
| `task-disable` | `target[]` `\Path\Name*` (that folder only), or `taskPath` (a folder, searched with all its subfolders) plus `target[]` name patterns (default `*`) | disables matching tasks; records each task's action identity (Execute, Arguments, ClassId). Every search prints its match count | re-enables only if the task still runs the recorded action |
| `file-placeholder-dir` | `target[]`, `stopHosts[]`, `createIfMissing`, `backup` | copies the file to `backup\` (hash-checked), stops processes by full path, deletes the file, creates a same-named folder (a repairer cannot write the file back) | if the folder is still empty: removes it and restores the file from the backup; without a backup it is listed for reinstall |
| `dir-placeholder-file` | `target[]`, `checkLoaded` (default true), `stopHosts[]`, `createIfMissing`, `backup` | stops the `stopHosts` processes by full path, re-checks loaded modules, copies the folder to `backup\` (file count checked), replaces it with an empty read-only file; deferred with WARN while any module under the folder is loaded or the check is incomplete (see Loaded-Module Check). Set `backup: false` for very large folders | if the file is still empty: removes it and restores the folder from the backup, else lists it for reinstall |
| `acl-deny-write` | `target[]`, `principal` (`CurrentUser`, `Users`, SID), `emptyFirst`, `createIfMissing` | adds exactly the missing deny rights (WriteData, AppendData, WriteEA, WriteAttributes; inherited by children on folders) for that SID; records which rights it added | takes away exactly those rights from that SID's entry with the same inheritance; other deny entries and rights stay; removes a folder it created |
| `ifeo-block` | `target[]` bare exe names | IFEO `Debugger` = `%SystemRoot%\System32\AppDebloat-blocked\<id>.exe` (never exists) | deletes only its own Debugger value, the key only if it created it |
| `reg-set` | `target` key, `name`+`value` or `values{}`, `kind` (DWord, QWord, String, ExpandString, MultiString), `view` | sets values, records the old ones | restores or deletes each value |
| `reg-delete-key` | `target[]`, optional `match` regex over subkeys, `view` | `reg export` to the state folder, then deletes; TrustedInstaller-owned keys are a WARN, not a FAIL (a known failure when `knownFailure` covers the key) | `reg import`, unless the key exists again (CONFLICT) |
| `shellext-block` | `clsids[]`, `handlerMatch`, `handlerParents[]`, `removeClsid`, `label` | `Shell Extensions\Blocked` values, deletes the CLSID keys and matching ContextMenuHandlers (HKLM and HKCU, 64-bit and WOW6432Node). A handler key whose name or default value is the CLSID with a trailing `-` (the vendor's own off switch) counts as the same CLSID | removes Blocked values, imports deleted keys |
| `toast-off` | `target[]` AppUserModelIDs (wildcards match existing) | `Notifications\Settings\<id>` `Enabled=0` | restores |
| `firewall-block-program` | `target[]` program paths, `direction` | rule `AppDebloat <id> <action> <exe> <hash>` in group `AppDebloat-<id>` | removes that rule only if its group and program are still the recorded ones |
| `hosts-block` | `target[]` domains, `acknowledgeFlagging` | discouraged, always printed as WARN; skipped unless acknowledged; refuses Microsoft domains | removes exactly the lines it added; the rest of the file is kept byte for byte |
| `preboot-file-edit` | `target[]` INI glob, `section`, `set{}`, `dropFromSections[]` | for settings the app keeps in shared memory and flushes back on exit: registers a one-shot SYSTEM startup task that edits the file before logon and deletes itself after success | cancels a pending edit (if the task still runs the recorded script), or schedules a restore before next logon for each file whose values are still exactly the written ones |
| `ini-set` | `path` (tokens, globs), `section`, `key`, `value` (string or number; `null` removes the key), `encoding`, `onlyWhenNotRunning[]` | for an INI the app reads at start: sets (or adds, or removes) one key, via a temp file and `Replace`; journals the original value and whether the section existed. Deferred with WARN while an `onlyWhenNotRunning` exe runs | only while the key still has the written value: puts the original back (or removes the key, and the section if the tool created it) |
| `json-set` | `path` (tokens, globs), `pointer` (JSON pointer, `/a/b~1c`), `value` (any JSON), `onlyWhenNotRunning[]` | replaces exactly the value at the pointer, or adds the missing member (and missing parent objects) at the start of the deepest existing object; the rest of the file is kept byte for byte. Deferred with WARN while an `onlyWhenNotRunning` exe runs | only while the value still equals what the tool wrote: puts the original text back, or removes the member it added |
| `hook` | `hook` name, `args{}` | app-specific logic, see below | the hook's `Undo` |

**Task Folders.** A `target` such as `\VendorUpdate*` searches only the root folder, so it cannot find tasks that a
Chromium-style updater registers under `\VendorUpdaterSystem\VendorUpdater\`. Use `taskPath` for those: it
matches the folder and every subfolder (wildcards allowed), and `target` then lists name patterns only.
`taskPath` must start with at least three literal characters and may not reach `\Microsoft\`; tasks under
`\Microsoft\` and the tool's own `<Prefix>Debloat-*` tasks are never matched. Every search is printed in every
mode, so a miss is visible instead of a plain SKIP:

```json
{ "id": "updater-tasks", "type": "task-disable", "category": "updater", "rationale": ["L-R6"], "evidence": "observed",
  "taskPath": "\\FabrikamUpdaterSystem\\", "target": ["FabrikamUpdater*"], "reapply": true }
```

```
[INFO] updater-tasks: searched \FabrikamUpdaterSystem\ and its subfolders for FabrikamUpdater*: 2 matches (...)
[INFO] updater-task: searched \FabrikamDrive\ (this folder only; taskPath also searches subfolders) for FabrikamDriveUpdateTask*: 0 matches
```

**Tasks the Dry Run Cannot See.** Without elevation, `Get-ScheduledTask` does not list tasks that only SYSTEM or
Administrators may read, which is where most vendor updater tasks live. A non-elevated run therefore appends
`(not elevated: SYSTEM tasks are invisible)` to every task search, so `0 matches` is never read as absence. When
`scripts/elevated_readonly.ps1 -Key <id>` has saved its task list to `%ProgramData%\AppDebloat\<id>\elevated-tasks.json`
(every task outside `\Microsoft\`, not only those that mention the app), the line also gives that list's count for
the same search and the date it was taken; the engine's own `<Prefix>Debloat-*` tasks and `\Microsoft\` are left out
of it as they are of the live search:

```
[INFO] updater-tasks: searched \FabrikamUpdaterSystem\ and its subfolders for FabrikamUpdater*: 0 matches (not elevated: SYSTEM tasks are invisible); last elevated enumeration (2030-01-01 09:30): 2 matches (...)
```

The saved count is information only: the plan lists what the live search found, and the elevated `-Apply` plans
from its own live search. The file may be a bare array of rows or `{captured_at, tasks: [rows]}`; a row names its task
by `path` and `name` (or `TaskPath` and `TaskName`, or `full_path`). The date is `captured_at`, else the file's time.
A file that cannot be read is reported on the same line. `-Uninstall` deletes it with the other state files.

Technique choice, least flagged first: placeholder and ACL, then service disable, then task disable, then a
per-program firewall rule, then IFEO, and hosts last. Security products remove IFEO keys and flag hosts edits, so
P6 re-reads them after a delay and after a reboot.

INI edits (`ini-set`, `preboot-file-edit`) keep the BOM and encoding and are written via a temp file and
`[IO.File]::Replace`. A BOM decides the encoding (UTF-16LE, UTF-8); without one, `ini-set` uses `encoding`
(`utf-8`, `utf-16le`, or a code page name or number such as `gbk` or `936`) and otherwise reads and writes the
bytes as Latin-1, which keeps any file intact as long as the key and value are ASCII. Set `encoding` whenever the
value is not ASCII. A new section is added before the file's trailing newline. A restore puts every original value
back; a key removed from a section comes back at the end of that section.

**Choosing Between the INI Types.** Use `ini-set` for a file the app reads at start and does not rewrite from
memory; give it `onlyWhenNotRunning` with the exe that owns the file, so the edit waits until the app is closed
instead of being overwritten on exit. Use `preboot-file-edit` only when the app keeps the settings in shared memory
and writes them back whenever it runs, so the edit must happen before logon.

**json-set.** The file is read as UTF-8 (a BOM, UTF-8 or UTF-16LE, is kept); anything that does not decode or parse
is a FAIL, never a guess. Only the value at `pointer` changes; formatting, key order and other members stay as they
were. A missing member is inserted as the first member of its deepest existing object, with any missing parent
objects; a pointer through a missing array element or into a scalar is refused, and `-` (array append) is not
supported. Values are compared after removing whitespace and normalizing string escapes, so `"a&b"` equals
`"a&b"`. Chromium and Electron note: keys protected by `Secure Preferences` MACs are reset by the browser when
edited from outside; `json-set` does not recompute MACs, so P6 must re-read the value after a restart.

```json
{ "id": "promo-banner", "type": "json-set", "category": "ad", "rationale": ["L-A5"], "evidence": "observed",
  "path": "{appData}\\settings.json", "pointer": "/promotions/showBanner", "value": false,
  "onlyWhenNotRunning": ["{root}\\ExampleApp.exe"] }
```

**onlyWhenNotRunning** lists exe paths (tokens allowed). A process with that image path, or a process of that name
whose path cannot be read, defers the action with a WARN at plan time and again right before the write; `-Uninstall`
reports the same as a WARN (journal kept). The engine never stops these processes itself.

## Known Failures

An item that keeps failing for a reason that is understood and cannot be fixed (a security suite that vetoes one
service change per item, for example) would make every `-Auto` run log a failure, so a new failure would look like
the old one. Record it on the action:

```json
"knownFailure": { "reason": "a security suite vetoes the start-type change (access denied, protection level NONE)", "ref": "L-R2" }
```

`reason` says why it fails and `ref` points at the ledger item or verification note that shows it; both are
required. Without `targets` it covers every item of the action. When only some targets fail, list them in `targets`,
so a new failure of another target stays a FAIL:

```json
{ "id": "updater-svc", "type": "service-disable", "target": ["FabrikamDriveUpdateSvc", "FabrikamDriveElevationSvc"],
  "knownFailure": { "reason": "...", "ref": "L-R2", "targets": ["FabrikamDriveElevationSvc"] }, ... }
```

Each `targets` entry names an item the way the action names its targets, with tokens expanded and `*` and `?`
allowed (case-insensitive): a service name, `\Folder\TaskName`, a file or folder path (`{root}\updater_*.exe`), a
bare exe name (`ifeo-block`), `HKCU\Key\ValueName` (`reg-set`, `shellext-block`, `toast-off`), `HKLM\Key` (deleted
keys), a program path (`firewall-block-program`) or the hook's own item `Key`. A registry entry may spell the hive
any way an action target may (`HKEY_CURRENT_USER\`, `HKCU:\`) and may end in `\`: both sides are compared as
`HKLM\...` or `HKCU\...` with no trailing backslash. `hosts-block` and `preboot-file-edit` plan one item per action
and take only the whole-action form. A failure while the plan is built (before any item exists) is a known failure
only under the whole-action form; with `targets` it stays a FAIL, since no target names it.

Every run (dry run included) lists the action under `Known Failures` as a WARN naming the reason and its targets,
so it is never forgotten. Each planned item it covers is marked `known to fail (ref ...)`, and the plan counts them
apart: `Plan: 4 change(s), 1 of them known to fail` and, at the end of a dry run,
`4 change(s) planned, 1 of them known to fail`. When a covered item fails, at plan time or while applying, the
failure is logged as `[WARN] [id] known failure (ref ...): reason :: item :: error` and counted as a known failure,
neither as a failure nor as a warning: it does not set exit code 1 and does not stop `-Install`. When a covered item
succeeds, an INFO line says to remove `knownFailure` once it stays fixed. The `-Auto` line in `history.log` stays
compact; it names each action once with its count, and the full text stays in `auto.log`:

```
2030-01-01T06:00:00 engine 1.4.0 fabrikam-drive 5.3.1|FabrikamDrive: 0 change(s), 0 failure(s), 1 known failure(s) [updater-svc x1, ref L-R2]
```

A failing `sc.exe` is reported without throwing, so a handled failure leaves no `TerminatingError` in the `auto.log`
transcript (PowerShell records every thrown error there, even a caught one). Record a knownFailure only after the
access-denied diagnostics (below) were read; never use it to hide a failure nobody explained.

## Access-Denied Diagnostics

When a change is refused with access denied (any language: HRESULT 0x80070005, Win32 error 5, the exception type
or the PermissionDenied category), the engine prints a read-only diagnostic block after the FAIL:

- service: its security descriptor (`sc sdshow`) and protection level (`sc qprotection`);
- registry (`reg-set`, `reg-delete-key`, `ifeo-block`, `shellext-block`): the key's owner and SDDL;
- file or folder (placeholders, ACL, INI and JSON edits): owner, attributes and SDDL;
- scheduled task: state, author and principal;
- once per run: the loaded file system minifilters (`fltmc filters`, elevated runs only) and the installed
  antivirus products (`root/SecurityCenter2` `AntiVirusProduct`).

A security suite can veto a change per item even when the permissions and protection level allow it. The engine
never works around a denial (no ownership change, no ACL rewrite, no retry as another account): record it as
`knownFailure` and use another lever (`reference/levers.md`). Items a `knownFailure` covers skip the block.

## Loaded-Module Check

`dir-placeholder-file` (with `checkLoaded`, the default) never replaces a folder while code from it is loaded. The
engine takes a Toolhelp32 snapshot of every process with `TH32CS_SNAPMODULE | TH32CS_SNAPMODULE32`, so 32-bit
modules inside WOW64 processes are seen, and matches by full module path: a module counts only when its path lies
under the target folder (case-insensitive prefix on the written path and on the folder's real path; 8.3 names are
resolved first). A DLL of the same file name loaded from somewhere else does not count.

- A process that loads a module from the folder defers the action with a WARN naming the process, PID and module.
  Processes listed in `stopHosts` are left out at plan time; right before the change the engine stops them by full
  path, takes a fresh snapshot and checks again.
- A process that cannot be inspected makes the result unknown, and unknown defers the action: it is never read as
  "not loaded". These kinds are exempt because they cannot hold the app's DLLs: kernel minimal processes (System,
  Registry, Memory Compression, Secure System, vmmem); protected processes (PP or PPL) whose image is outside the
  install root, since those load only DLLs signed for their protection level; isolated security processes
  (`LsaIso.exe`, `NgcIso.exe`, VBS trustlets present whenever VBS or Credential Guard is on) and VM memory processes
  (`vmmem*`, such as `vmmemCmZygote`); and any process unreadable with error 998 whose image is under System32. The
  last two kinds are exempted only when the image is unknown or under System32, so an app process that borrows the
  name is still checked. Each run prints which processes were exempted:

```
[INFO] loaded-module check exempted (cannot load app code): LsaIso (PID 1376, error 5: isolated security process (VBS trustlet)); ...
```

- For any other uninspectable process that you have checked cannot hold the app's code, pass
  `-IgnoreUninspectable <names>` (this run only) or list it in the manifest's `checkLoadedExempt` (also used by the
  watch task). Both take process names with wildcards (not only wildcards) and skip a matching process only while
  it cannot be inspected; a process that can be inspected is always checked. The header prints the list, the run
  prints each process it skipped, and every change the choice allowed gets a `kind: "note"` journal line naming the
  skipped processes and the patterns with their source.
- The dry run is not elevated and cannot inspect other users' or SYSTEM processes. It still lists the item, marked
  `[loaded-module check incomplete without elevation: N process(es) could not be inspected; -Apply checks again]`;
  the elevated `-Apply` runs the full check (with SeDebugPrivilege enabled in its own token) and defers if anything
  stays unknown.

## Hooks

For gates that do not fit a type (an encrypted config, a vendor component table). The hooks file adds entries to
`$Hooks`:

```powershell
$Hooks['vendor-gate'] = @{
    Plan  = { param($Ctx, $Action) <# return nothing when compliant, else one hashtable per change #>
              @{ Key = 'unique-id'; Desc = 'what changes'; Data = @{...}; Original = @{...}; After = [ordered]@{...} } }
    Apply = { param($Ctx, $Data, $Item) ... }
    Undo  = { param($Ctx, $Data, $Original, $Entry) ... }   # optional; missing = WARN on -Uninstall
}
```

`After` is the state Apply writes; it is journaled before Apply runs and reaches Undo as `$Entry.after`. Undo must
restore only when the current state still equals it, and return a string: `CONFLICT <why>` (left as is),
`SKIP <why>` (already original), `GONE <why>`, `WARN <why>`, `REINSTALL <path>`, or nothing on success. A WARN or
CONFLICT keeps the journal (see `-Uninstall`). `examples/contoso-pinyin` shows the pattern.

Hooks run inside the script, so they may call `Expand-AdPath`, `Assert-AdPathSafe` (call it before touching any
path; add `-EditInPlace` when the hook edits the content of a `core.preserve` file), `Stop-AdProcessByPath`,
`Get-AdRunningByPath`, `Get-AdRegValue`, `Set-AdRegValue`, `Update-AdIni`, `Read-AdTextFile`, `Write-AdTextFile`,
`Say` and `AdGet`. An `Apply` that fails in an expected way (a known failure) may `return (New-AdFailure 'why' <code>)`
instead of throwing: it is handled exactly like a thrown error but leaves no `TerminatingError` in `auto.log`
(code 5 marks an access denial). Prefer `ini-set` or `json-set` over a hook whenever the setting is a plain INI key or JSON
value. `$Action.args` carries the manifest arguments. Never embed a key, decrypted config or other vendor-derived secret in a hook:
derive it at run time from the user's own install and keep it in memory.

## Modes and Exit Codes

| Mode | Behavior |
|---|---|
| (none) | dry run: resolves, prints the header (root, how it was found, identity), the numbered plan (items a `knownFailure` covers are marked and counted apart), the inactive actions and the options not selected; changes nothing, needs no elevation (task searches then say what they cannot see, see Task Folders) |
| `-Apply` | builds the same plan, prints it, then executes exactly those items |
| `-Install` | refuses if a task named `<Prefix>Debloat-Watch` exists that the journal does not record; applies the plan first; then, only when the apply had no failures (known failures do not count), copies the script to `%ProgramData%\AppDebloat\<id>\<Prefix>Debloat.ps1` (SYSTEM and Administrators full, Users read), saves options to `options.json`, journals and registers `<Prefix>Debloat-Watch` (logon + every 6 h, current user, highest, `conhost --headless`). After a failed apply it registers nothing, prints `Watch task NOT registered` with the reason and exits 1 |
| `-Auto` | used by the watch task: saved options, only `reapply: true` actions, transcript to `auto.log`, one line per run in `history.log` (changes, failures, known failures as `[action-id xN, ref R]`, other WARN text, fingerprint changes, refusals) |
| `-Uninstall` | replays the journal in reverse (see below), prints the vendor files that need a reinstall; works even when the app is gone |

At most one of `-Apply`, `-Install`, `-Uninstall`, `-Auto` per run: a combination is refused with exit 2 before
anything else runs (`Resolve-AdMode`). `-IgnoreUninspectable <names>` combines with any mode (see Loaded-Module
Check).

`-Uninstall` undoes only what the journal records as written by this tool: tasks, IFEO values and firewall rules
are removed only when the journal created them and they still match the recorded identity. Each entry that is
undone cleanly gets an `undone` journal line, so a rerun never replays it. Any WARN, CONFLICT or failure is counted:
the journal and the state folder are kept, a summary lists every item left behind, and the exit code is 1. Resolve
the items by hand and run `-Uninstall` again. When nothing is left, the engine deletes only the files it writes in
the state folder (journal, options, state, logs, backups, exports, its own scripts, the saved elevated task list)
and the folder if it is then empty.

Exit 0 ok, 1 at least one FAIL (plan-time refusals included) or an `-Uninstall` that left items behind, 2 refused
before any change (more than one mode, not elevated, invalid manifest, app not found, root refused or failing the
identity check, unsupported or unreadable version, a foreign watch task). WARN-only items do not count as changes.

Install the watch task only after the core-function probe passed (P6); a task that re-applies a broken plan every
6 hours is worse than none.

## Safety Rules the Engine Enforces

- Paths: refuses empty paths, drive roots, UNC, `%SystemRoot%` and System32/SysWOW64, Program Files roots,
  ProgramData, `C:\Users`, the user profile and its AppData roots, TEMP. A target must lie under the install root or
  an `allowedRoots` entry (an allowed root, but never the install root, may itself be the target). Any reparse
  point between the base and the target is refused. `..` is normalized before the check. The target's real path
  (nearest existing ancestor resolved by handle, the missing rest appended) must also lie under the base's real
  path, so a junction above the root cannot carry a change outside it; a path that cannot be resolved is refused.
- Core contract: refuses actions on core files, folders containing them, core services and core processes.
  `core.preserve` files may only be edited in place (`ini-set`, `json-set`, `preboot-file-edit`, a hook with
  `-EditInPlace`); any other action on them or on a folder that contains them is refused.
- Folders are replaced only after the loaded-module check (full module paths, 32-bit modules included) found no
  module under them and could inspect every process that matters; unknown defers, it never passes.
- Processes are stopped only by exact full-path match, then by PID. A process of that name whose path cannot be
  read is an error, not a non-match, and a process still running after the stop is a FAIL.
- Failed queries are never read as absence: a failed service, scheduled task or firewall-rule query fails the
  action (or the undo step) instead of being treated as "not present". Existence lookups produce no error record
  for a plain miss (tasks come from one full enumeration, firewall rules are queried with `SilentlyContinue` and
  only `ObjectNotFound` is accepted, services and registry return null), so transcripts and `auto.log` show no
  `TerminatingError` for "not found". A failing `sc.exe config` and a service that does not stop are reported
  without throwing too, so a handled failure (a known failure, a WARN) is not logged as one either.
- IFEO: bare vendor exe names only; refuses generic names (updater.exe, setup.exe, crashpad_handler.exe, ...) and
  any name that exists in System32 or SysWOW64.
- Registry deletes: refuses keys shallower than three levels, shared roots (`Software\Classes\CLSID`, Run, ...)
  and anything under `SYSTEM\CurrentControlSet\Services` (services are disabled, never deleted).
- No `sc delete`, no binary patching, no Defender changes, no Microsoft domains in hosts.

## Journal

`%ProgramData%\AppDebloat\<id>\journal.jsonl`, append-only, one JSON object per line.

- `kind: "change"` is written BEFORE the change it describes (write-ahead), so an interrupted `-Apply` can be
  rolled back: `ts, app, actionId, actionType, prim, key, desc, reversible, evidence, version, data, original,
  after`. `original` is the state found; `after` is the state the tool is about to write.
- The `key` identifies the changed object (`fs:<path>`, `reg:<hive><view>\<key>|<value>`, `ifeo:<exe>`,
  `svc:<name>`, `acl:<path>|<sid>`, `ini:<path>|<section>|<key>`, `json:<path>|<pointer>`, `watchtask:<name>`, ...). The first `original` for a key wins forever: a rerun
  after the vendor reset something does not overwrite the true original. A later line for the same key only
  updates `after` (for example when a rebuilt manifest writes a different value).
- `kind: "undone"` closes a key after `-Uninstall` restored it cleanly.
- `kind: "note"` records a choice, not a change (today: the processes the loaded-module check skipped by
  `-IgnoreUninspectable` or `checkLoadedExempt`, with `actionId`, `key`, `skipped` and `patterns`); `-Uninstall`
  ignores it.
- If the run stops between the journal line and the change, the undo finds the original still in place and reports
  SKIP; a half-made change shows up as CONFLICT instead of being overwritten.

Deleted registry keys are exported to `regkeys\`, replaced files and folders are copied to `backup\` before the
journal line is written. The journal and backups are DATA: they stay on the machine and never go into a public repo.
